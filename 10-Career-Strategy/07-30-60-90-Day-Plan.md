# 30-60-90 Day Plan

> Onboarding is a delivery problem: build trust, learn the system, and create visible value without fake heroics.

---

## Purpose

Provide a practical onboarding guide for Senior / Lead / Tech Lead / Architect hires: first week through first 90 days — trust, codebase, architecture, stakeholders, quick wins, documentation, mentoring, and ownership.

---

## Key Takeaways

- Days 1–30: listen harder than you propose.
- Quick wins should reduce risk or friction — not rewrite the platform.
- Write down architecture as you learn; don’t trust memory.
- Credibility comes from reliable small deliveries + clear communication.
- By day 90, you should own a problem space, not only tickets.

## First Week

### Goals

- Access, tooling, and security training done.
- Know team mission, SLOs, on-call basics.
- Map the service landscape at a sketch level.
- Meet manager: success criteria for 30/60/90.

### Actions

| Day | Focus |
|-----|-------|
| 1 | HR/IT, intro, clone repos, run app locally if possible |
| 2 | Read README/ADRs; deploy pipeline walkthrough |
| 3 | Shadow standups; identify critical paths |
| 4 | Pair on a small bugfix / test |
| 5 | Weekly note to manager: learnings + questions |

### Professional communication — manager sync

> By end of week 1 I want: local run working, a sketch of our service boundaries, and agreement on what “useful” looks like by day 30. What would you add?

### Checklist — Week 1

- [ ] Slack/Teams channels joined; on-call doc read
- [ ] Can run or explain why not yet
- [ ] List of top 5 systems + owners
- [ ] 1:1 cadence set with manager
- [ ] No public architecture pronouncements yet

## First Month (Days 1–30)

### Goals

- Build trust through curiosity and reliability.
- Ship 1–2 small, reviewed changes to production.
- Understand architecture and failure modes for your domain.
- Meet stakeholders: product, QA, SRE, dependent teams.

### Learning the codebase

**Decision framework — reading order**

1. Entry points (API controllers / consumers)
2. Domain core (entities, invariants)
3. Persistence and transactions
4. Integration boundaries (payments, identity, messaging)
5. Observability (dashboards, alerts)
6. Tests that document behavior

### Understanding architecture

Produce a personal **Architecture Learning Doc** (private or team wiki):

```text
Context diagram
Critical user/company journeys
Data stores and consistency notes
Async flows / outbox / retries
Known debt and landmines
Open questions
```

### Meeting stakeholders

| Stakeholder | Ask |
|-------------|-----|
| Product | Roadmap pressure; definition of done |
| SRE/Platform | SLOs, toil, deploy risks |
| Dependent team leads | Contracts that break |
| QA | Where bugs cluster |
| Support | Top customer pain |

### Quick wins (good vs bad)

| Good | Bad |
|------|-----|
| Fix flaky test blocking CI | Big-bang rewrite proposal |
| Improve runbook for recurring page | Quietly change public API semantics |
| Add missing dashboard for known blind spot | Reformatting entire modules |
| Document onboarding hole you hit | Criticizing predecessors in public |

### Checklist — Day 30

- [ ] ≥1 production change shipped
- [ ] Architecture learning doc v1
- [ ] Stakeholder map with names
- [ ] Feedback from manager on trajectory
- [ ] On-call shadow completed if applicable

## First 60 Days

### Goals

- Own a thin vertical slice of a meaningful problem.
- Participate credibly in design reviews.
- Begin mentoring lightly (pair, review).
- Reduce bus factor in one area you touched.

### Technical credibility moves

- Ask precise questions in RFCs (“failure mode if broker lags?”).
- In code review: prioritize correctness, security, operability over style nits.
- Volunteer for an incident retrospective action — and close it.

### Documentation

Upgrade learning doc → shared ADR or wiki page where gaps hurt the team.

### Mentoring

Offer pairing to a junior on something you just learned — teaching consolidates your model and builds goodwill.

### Checklist — Day 60

- [ ] Named owner (or co-owner) of a component / epic slice
- [ ] Active in design review with written feedback
- [ ] One shared doc merged
- [ ] Midpoint 1:1: adjust 90-day goals

## First 90 Days

### Goals

- Clear ownership: a problem space with metrics.
- Demonstrable impact: reliability, delivery speed, or risk reduction.
- Trusted voice in architecture discussions for your domain.
- Personal brand inside the company: reliable, calm, specific.

### Ownership definition

Ownership ≠ doing all the code. Ownership = ensuring outcomes: quality bar, risk calls, sequencing, and escalation.

### Deliverables sketch (Lead example)

- Migration phase 1 complete or roadmap locked with metrics
- On-call pain reduced by X (noise alerts tuned)
- Team agreement on API guidelines for new endpoints
- Successor-ready notes for anything you uniquely know

### Checklist — Day 90

- [ ] Manager agrees you’ve met (or renegotiated) success criteria
- [ ] Impact narrative written (for promo / self later)
- [ ] Feedback collected from ≥2 peers
- [ ] Next-quarter plan drafted

## Building Trust

### Behaviors that work

- Say “I don’t know yet” + return with findings.
- Hit small deadlines you commit to.
- Credit others publicly; escalate risks privately early.
- Learn team norms before importing previous-company rituals wholesale.

### Behaviors that destroy trust

- Drive-by rewrites.
- Review snark.
- Skipping meetings you later criticize.
- Surprising production with “improvements.”

## Decision Framework — What to Optimize by Horizon

| Horizon | Optimize |
|---------|----------|
| Week 1 | Access + relationships + map |
| Day 30 | Learning velocity + small shipped value |
| Day 60 | Owned slice + review credibility |
| Day 90 | Outcome ownership + trust capital |

---

## Real-World Examples

- **Fintech Lead:** First month fixed reconciliation report mismatch (+ tests); month two owned cutover checklist for a provider switch; month three ran a tabletop incident drill.
- **GovTech:** Spent week two on security/threat-model onboarding; quick win was improving audit-log documentation used by compliance — high trust, low glamour.
- **Distributed product team:** Published a crisp RFC on idempotency keys; credibility rose faster than coding volume alone.

## Common Mistakes

- Staying silent for 45 days then proposing a rebuild.
- Optimizing for looking busy over learning critical paths.
- Ignoring on-call culture until you’re primary.
- Measuring success only by story points.

---

## Reflection Questions

1. Who trusts you today that didn’t on day 1 — and why?
2. What is still fuzzy in the architecture, and what’s your plan to resolve it?
3. What quick win reduced real pain vs performing productivity?
